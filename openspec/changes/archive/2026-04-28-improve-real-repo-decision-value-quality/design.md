## Context

The v0.3 platform foundation now supports real stack validation, login/scope, GitHub App operations, and private repository access hardening. The next product risk is no longer whether a real repository can be imported; it is whether the imported review candidates are useful enough for a reviewer to establish the first accepted baseline quickly and then trust why/drift only where evidence supports it.

Existing code already exposes candidate review evidence, source refs, artifact provenance, readiness, and benchmark fixtures. This change should improve the quality signals and reporting around those existing structures rather than rewrite the extraction pipeline or introduce a new review workflow.

## Goals / Non-Goals

**Goals:**

- Make imported candidate review cards easier to judge by surfacing compact quality cues: source-ref strength, artifact provenance, confidence, and extraction context.
- Reduce false equivalence between strong candidates and thin/low-value candidates by labeling weak evidence clearly.
- Make the first accepted imported decision feel like a milestone while keeping why/drift trust bounded to matching grounded questions.
- Add or update real-repo quality reports so curated repository validation records candidate value observations, not just pass/fail readiness.
- Keep implementation bounded to current data models and current review actions.

**Non-Goals:**

- No full extraction pipeline rewrite.
- No new LLM prompt architecture unless a small bounded copy/metadata improvement is necessary.
- No multiplayer review, approval workflow, or assignment system.
- No hard-coded repository-specific product logic.
- No live provider requirement in default CI.

## Decisions

1. Use quality labeling before filtering.

   The first implementation should not silently discard candidates unless the current pipeline already classifies them as invalid. Instead, product and validation surfaces should expose quality labels such as strong, partial, or thin so reviewers can make informed decisions. Alternative considered: aggressively filter low-value candidates. Rejected because it risks hiding useful but imperfect imported decisions without enough validation data.

2. Reuse existing source refs and artifact provenance as the primary quality signal.

   Source-ref count, previewable quotes, artifact type/title/repo/url, confidence, and extraction family are already available or close to available. Reusing these keeps the slice small and testable. Alternative considered: add a new scoring table. Rejected because it adds persistence and calibration work before the product has enough real-repo observations.

3. Keep first-baseline guidance bounded.

   Accepting the first imported candidate should change product guidance, but it must not imply every why answer is trusted. The UI should route users toward why/drift while explaining that support still depends on matching source refs and same-thread evidence.

4. Treat quality reporting as an operator artifact.

   The quality report should summarize curated repository observations, candidate counts, thin-evidence pressure, and follow-ups. It should not become a default release blocker that requires live providers.

## Risks / Trade-offs

- [Risk] Quality labels can feel subjective. -> Mitigation: base the first cut on observable data: source-ref count, preview availability, artifact provenance, and confidence.
- [Risk] Adding too much review-card detail can slow reviewers down. -> Mitigation: keep the default card compact and link to details for full context.
- [Risk] Reports may become stale. -> Mitigation: record command/date/scope and keep live validation outside default CI.
- [Risk] Improving UI without extraction changes may not reduce truly bad candidates enough. -> Mitigation: record residual low-value patterns as deferred extraction follow-up rather than expanding this change.

## Migration Plan

- No database migration is expected.
- Existing review payloads and workspace readiness should remain backward compatible.
- If a new computed quality label is added, derive it at read time from existing fields where possible.
- Rollback is limited to removing new labels/copy/reporting; stored decisions and source refs remain compatible.

## Open Questions

- Whether the first implementation should expose `extraction_family` directly or translate it into a reviewer-facing provenance label.
- Whether the quality report should be a static markdown update or generated by a script from current benchmark fixtures.
