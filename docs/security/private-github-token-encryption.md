# GitHub private Token encryption, migration and rotation

**Scope:** PR #7 owner-scoped GitHub personal access tokens only. This is an operator procedure, not a general KMS solution. Tokens used via the separate global `GITHUB_TOKEN` setting are runtime environment secrets, not stored in `github_token_access_sources`.

## Security invariants

- Owner-scoped tokens are encrypted using `cryptography.fernet.Fernet` (authenticated encryption with a random IV). Stored `token_secret` envelopes look like `enc:v1:<key-id>:<ciphertext>`. The plaintext JSON inside encryption binds `owner_scope`, `source_ref`, and `repo_identity` to the token; reassigned ciphertext fails validation.
- **Never** store an encryption key in SQLite/PostgreSQL, Git, workflow logs, or a user-facing API response. Keep keys only in your deployment's secret manager / securely injected environment.
- No encryption key means private-token bind/read fails. Legacy unencrypted DB values are never read by the web/API application, including in `development` or `test`. Recover through explicit offline migration or reauthorize.
- Losing all historical keys permanently prevents decrypting stored tokens. Back up keys separately, under restricted access. Fernet protects credential confidentiality/integrity, **not** full-database access, session tokens, source artifacts or application availability.
- The example key below is generated by each operator at runtime. Do not use the deterministic key in `tests/conftest.py` outside tests.

## Setup

On your administrator-controlled host with Python/Engine dependencies:

```shell
uv run --project services/engine python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Store the generated key in your secret manager; set Engine environment value:

```text
GITHUB_TOKEN_ENCRYPTION_KEYS=primary2026=<YOUR_NEW_FERNET_KEY>
```

Comma-separated keys are supported in **newest-first** order, e.g.
`primary2026=<NEW>,old2025=<OLD>`. Each key ID is a unique 1–32-character ASCII identifier made of letters, numbers, `_`, `-`. Every loaded Engine instance must use a compatible list during rollout; the first key encrypts new writes. Values are ordinary Fernet URL-safe base64 keys produced by the command above (not passwords).

`APP_ENV=production` now accepts private-token binding **only if** a valid key is configured. Restart Engine after setting keys; do not depend on process-global runtime toggles.

## Safe migration of existing plaintext DB rows

1. **Stop the Engine and background workers**. Pause imports and ensure there are no in-flight token writes. Make a restricted, encrypted, restorable DB backup; remember SQLite WAL files and PostgreSQL backups may still contain plaintext. Do not upload the DB or backups to GitHub Actions Artifacts.
2. Configure `DATABASE_URL` for the intended database and at least one Fernet key in `GITHUB_TOKEN_ENCRYPTION_KEYS`. Prefer a new key stored outside the database.
3. Check whether plaintext exists without printing any token:
   ```shell
   uv run --project services/engine python scripts/security/migrate_github_tokens.py --include-legacy
   ```
   Dry run validates all present ciphertexts and prints **counts only**. Without `--include-legacy` the command refuses to process plaintext rows.
4. Apply **explicitly**:
   ```shell
   uv run --project services/engine python scripts/security/migrate_github_tokens.py --apply --include-legacy
   ```
   A failure rolls the transaction back, including any in-progress rotations.
5. Rerun without legacy allowance:
   ```shell
   uv run --project services/engine python scripts/security/migrate_github_tokens.py
   ```
   Confirm `legacy=0`, `rotate=0`; only then restart the Engine and test authorized private import.
6. **Rotate/revoke affected GitHub PATs** after migration, especially if older backups/logs had plaintext. Encryption of the current DB cannot retroactively purge backups, WAL pages or leaked tokens. Validate your encrypted-backup restoration procedure.

## Key rotation (no plaintext fallback)

1. Back up database and old keys securely, and stop all Engine writers.
2. Set `GITHUB_TOKEN_ENCRYPTION_KEYS=new_id=<NEW>,old_id=<OLD>`; distribute consistently to all Engine hosts.
3. Dry-run the tool without legacy flag. It authenticates every stored envelope and reports `needs_rotation` counts.
4. Run the tool with `--apply` (without `--include-legacy`), then dry-run once more to confirm `rotate=0` and `legacy=0`.
5. Restart and verify existing private imports. Only then remove old keys from the live keyring. Keep recovery copies of old keys per your backup retention policy.
6. A ciphertext tied to an unknown key ID, mismatched source context, or modified payload blocks migration; do not replace it with random ciphertext or silently skip it. Reauthorize that source if the original key cannot be recovered.

## Acceptance limitations

- The shipped implementation supports one Engine process's owner-scoped token encryption and an **offline** rotation tool; it is not online zero-downtime KMS rotation.
- No secret manager, distributed worker queue or hardened production hosting is provisioned by this PR. Do not mark the broader production-security gate complete without reviewing those deployment choices.
- The `pallets/click` public-import Action does not require any of these private tokens or encryption secrets and must remain independent.
